What the system does

The browser is the presenter interface. The Python server owns the experiment. Trusted numerical algorithms produce feasible sign vectors; an independent harness measures their cuts. Luna proposes changes to solver programs. The controller validates those changes, runs them and selects the next parents.

There are two nested searches. The outer evolutionary search changes a solver program. The inner numerical search executes that program to find a partition. The partition is a feasible witness used for evaluation. It is not a member of the program population. The language model is the outer mutation operator; it is neither the numerical executor nor the fitness authority.

The implementation is local, not a deployed multi-service platform. Start it with python demo/server.py --port 8766 --rounds 3, then open the presentation hub. Only the model worker makes an external API request. Visiting a page, reading a snapshot, reconnecting or replaying recorded evidence cannot buy a new model generation.

Architecture flow chart

The scorer is checked in two places: inside the numerical adapter and again in the controller after a worker returns. “Selection” and “event feed” are controller responsibilities, not additional network services. The API worker contains the credential boundary: its environment supplies the key; the browser never does.

Write actions require same-origin checks and a run or bootstrap write token. Start is idempotent: a second click does not create a second controller. Reading SSE never starts a controller. There is no generic shell, file-write or file-read endpoint. Static assets and private presenter aids have fixed allowlisted routes.

Initial population and numerical execution

The checkboxes choose the seed population P0P_0. Each checked kernel contributes its disclosed initial program. All four trusted kernels remain available to Luna when it proposes children. This distinction is deliberate: changing initialization is a different experiment from restricting the allowed hypothesis space.

The seed programs are:

Full name Initial configuration
Tabu Search tenure 5, no stagnation restart, 800 iterations
Simulated Annealing temperature 2 to 0.01, polish enabled, 6000 proposals
Breakout Local Search disclosed defaults, 700 flips
Rank-two Burer–Monteiro method 20 sweeps, 8 rounding directions, one solve

At Start, the new population protocol constructs raw sign vectors from seeds s,s+1,s+2s,s+1,s+2 modulo 2322^{32} and freezes them. Every seed program and every child receives a copy of those same vectors. No candidate inherits an undisclosed final assignment from another competitor. Within a multistage program, however, fresh=false passes the best retained witness from one stage to the next. fresh=true starts that stage’s own seeded exploratory state while protecting the old best if it remains better.

Execution version retained-bm-refinement-v1 makes a retained Burer–Monteiro stage after stage one consume the incoming partition as a geometric starting point: map signs to angles 0 or pi, add reproducible uniform angular offsets in [-0.35, 0.35] radians, then use the unchanged vector optimization, rounding and local-polish primitives. Retain the better incoming or returned partition. Thus Burer–Monteiro → Tabu Search passes a partition to discrete search; Tabu Search → Burer–Monteiro now genuinely refines vectors around the retained partition. demo/bm_refinement.py owns this adaptation; the vendor snapshot is unchanged. First-stage and fresh Burer–Monteiro calls retain their original independent vector search, preserving the measured initial solver screen.

Replacing a parent with a one-stage child is a different operation: that child starts from the common raw trial labels, not the previously evaluated parent’s output. The execution version and start rules enter new run records and Luna’s context. Stage results expose initialization, incoming/retained cut and allocated seconds. Earlier replays retain their original behavior and are not evidence for this newly added warm refinement.

Numerical allowance is 8 seconds per current comparison or dense-case trial. The historical torus retains its 1.5-second allowance. That clock covers all stages of one program. Remaining time is divided among remaining stages; unused time carries forward. Process startup has a separate bounded allowance. Kernel-specific work caps are additional limits, not a claim that iterations, proposals, flips and rounding directions cost the same amount.

The original torus recordings from the previous single-parent protocol remain available as legacy evidence. Their frozen warm-start construction is not silently reinterpreted as the new raw-start population protocol. New records carry the initial solver selection, scenario and protocol explicitly.

How one Luna request is created

  1. The round gate exposes the selected parent programs to the presenter.
  2. Run.propose takes up to three complete survivors and their measured evidence.
  3. proposals.context combines those records with history, constraints and budget.
  4. The controller saves a request description and increments the call count.
  5. An owned model_worker.py subprocess creates the actual Chat Completions body.
  6. The worker adds the credential as an HTTPS Authorization header and sends one request to the fixed TAMU endpoint.
  7. Public response chunks are recorded and relayed as real events.

The actual body uses model protected.gpt-5.6-luna, two messages and streaming. The completion limit is 2400 tokens, reasoning effort is low, and tool lists are empty. The system message contains instructions and the required output schema. The user message contains the serialized round context. TAMU’s transport uses https://chat-api.tamu.ai/api/chat/completions; it is not assumed to accept the direct OpenAI Responses protocol.

The exact exchange page shows the actual recorded body and public return. Its display excludes the Authorization header. A replay keeps a persistent label and withholds future received text until its recorded response time. This prevents a prerecorded answer from appearing to be a new model result.

The model does not receive solution vectors, stored replay, the preset numerical comparison, benchmark name, reference target or API key in this context. The fixed evaluator retains the graph and original edge weights. This makes the model a strategy proposer rather than an answer-copying or self-grading service. No model weights are trained or updated during the search; the external context and selected programs carry learning across calls.

How the response becomes measured evidence

The public answer must finish as JSON with the expected round, known parent IDs, a short hypothesis, mutation category, up to two children and an optional plateau reason. The controller validates each child’s allowed stage fields, numerical bounds, work caps and normalized identity. Invalid or duplicate children are rejected without a silent repair or free retry.

Every admitted program runs serially on the frozen starts. The backend accepts only original-order integer signs in {-1,+1}; it pins graph bytes by SHA-256 and recomputes the cut using two independent scoring paths. The parent controller checks the returned graph identity and recomputes witness quality again. A reported model score has no authority.

A program ranks only when all three trials and every required stage complete. Rank complete programs by higher median cut, higher minimum cut, fewer stages, then stable genome identity. Keep at most three from parents plus children. Separately retain the best valid witness, including one from an incomplete trial. The next context contains the surviving programs and measured failures.

Timing, cancellation and modes

The live profile permits three calls, two children per call, one to three stages per program and serial trials. Each model call is bounded by 35 seconds. The run deadline is 240 seconds, with owned cleanup by 250 seconds. Guided inspection pauses consume the same deadline. A successful reference match does not force an early stop in the teaching profile, so report calls-to-first-target separately from later demonstration calls.

Stop and Reset identify owned processes by PID and start tick, not by a broad process-name kill. Reset refuses to create overlapping work while cleanup is pending. The real-provider Stop path was exercised in the prior revision. Closing the local connection cannot establish that remote computation or billing ends instantaneously.

  • LIVE LLM: actual new provider proposals.
  • NUMERICAL ONLY: disclosed fixed comparison program; zero model calls.
  • RECORDED LLM REPLAY: verified prior live events; zero new calls, original model identity and timing distinct from playback speed.

No mode silently turns into another. Hidden reasoning is excluded from logs and UI; public output, completion metadata and provider-reported usage are retained.

The three demonstrations and what they establish

The old torus quickly saturated near reference 68. The presenter requested a case with clearer algorithm differences. Five supplied public graphs were screened using normalized classroom programs, identical raw seeds 3/4/5 and fixed work limits. The selected rand_pm_1000_s23.txt has 1000 vertices and 5043 signed edges, SHA-256 ebb1ee5df894bb2159cd29b2a65d237fa72c9d1fdc2080b2cc7cdb16f25a0503, and supplied unproven reference 1098. Only graph input and scalar reference metadata were imported. Public source records are:

  • Graph provenance: data/comparison_instance_provenance.json.
  • Normalized numerical screen, in demo/evidence/: replacement_instance_screen_normalized.json.

These values use explicit normalized classroom defaults, including the Breakout Local Search configuration. A preliminary direct-dispatch screen used that kernel’s implicit defaults and is not the current comparison evidence.

Preset 1 checks Tabu Search and Simulated Annealing. Preset 2 checks Tabu Search, Breakout Local Search and Burer–Monteiro. Graph, starts, seeds, caps, mutation space and ranking remain fixed. More seed programs cost more initial evaluations. Burer–Monteiro is included because of measured performance here, not because every evolutionary algorithm should start from it. The earlier BM-only torus control is preserved as history, not retained as the current recommended starting suite.

The informed run’s longer Burer–Monteiro → Breakout Local Search proposals left incomplete trials. Their witnesses remained valid; their programs were excluded. Its second response named an ineligible parent, so validation stopped the run. This is a genuine provider failure case with recorded context and public response, not a successful optimization run. The stronger initial suite did not establish a faster or more effective full search in these observations. Do not force that story.

The six newly authorized attempts are exhausted: two network-sandbox DNS failures before provider contact, then four real Luna calls across the two replacement runs. No retries or further calls are hidden. Both valid finished and valid failed sources can be replayed with their original terminal status; transport failures without verified model results are ineligible for genuine replay.

The third case is a separate dense real-weight stress test: 100 vertices, 4950 edges, reference 402.5209. Its preserved three-call genuine run matched all three trials after one call at 16.091s and finished at 56.602s. Sparse-1000 and dense-100 have similar edge counts but very different degree, density and weights. This is a transfer test; greater density does not establish a universal hardness ordering.

One run per condition cannot establish a causal effect or model superiority. The screened seeds are teaching evidence, not a held-out evaluation. Human prior-design effort is also absent from the run clock. All references are unproven.
