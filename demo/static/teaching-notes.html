1. LLM-Driven Evolutionary Search: Evolving packing programs

Can we improve the programs that find good circle packings?

ENGR 689 · Chapter 10 · Texas A&M University

First we will explain the circle-packing problem and what makes one arrangement better than another. Then we will use the evolutionary framework in Chapter 10 to improve programs that search for these arrangements. The two demonstrations use 26 and 32 circles. These are the published mathematical tasks from AlphaEvolve. 2. Circle packing: the problem

What are we trying to arrange?

Place 26 or 32 circles inside a square with side length 1. Choose each circle’s center (its location) and radius (half its width). The radii may differ.

Every circle must stay inside the square. Circles may touch each other and the boundary, but they must not overlap.

A valid packing satisfies these rules for every circle. The number of circles stays fixed within each problem.

Begin with the geometry before introducing an algorithm. A center is the point in the middle of a circle. A radius is the distance from that center to its edge, so the diameter is twice the radius. A unit square has side length one. In each problem the number of circles is fixed: 26 for Demo 1 and 32 for Demo 2. Their sizes can differ. We choose both their centers and their radii.

The picture shows four circles so the rules are easy to see. It is an illustration, not the 26- or 32-circle demo output. The dot marks one center and the segment labeled r runs from that center to the circle’s edge. Its plotted center/radius triples are (0.22,0.22,0.22), (0.74,0.22,0.18), (0.25,0.72,0.18), and (0.72,0.72,0.25). All circles fit inside the square and their interiors are disjoint.

A packing is valid only if every circle lies entirely inside the square and no two circle interiors overlap. Touching is allowed. For a center ci=(xi,yi)c_i=(x_i,y_i) and radius rir_i, these rules are ri≥0r_i\ge0, ri≤xi≤1−rir_i\le x_i\le1-r_i, ri≤yi≤1−rir_i\le y_i\le1-r_i, and ∥ci−cj∥2≥ri+rj\|c_i-c_j\|_2\ge r_i+r_j for each distinct pair. Zero radii are allowed under the demonstration’s contract and remain visible in its reports. The next frame introduces the score, separately from these validity rules.

The two cases use the mathematical formulation in AlphaEvolve Appendix B.12 (AlphaEvolve team 2025). The local initial methods, controller, Luna model and compute budget are our classroom implementation. No published answer coordinates are hidden in the initial arrangements.

3. Circle packing: the goal

Which valid packing is better?

Packing score: S=r1+⋯+rNS=r_1+\cdots+r_N, the sum of all radii. Larger is better.

B has the larger score. Circle positions limit how large the radii can be. We need a strategy to search for better packings.

Ask students to add the radii before revealing the conclusion. Point to the visible space around A’s circles and then to the touching circles in B. Four times 0.15 is 0.60. Four times 0.25 is 1.00. Both drawings use centers (0.25,0.25), (0.75,0.25), (0.25,0.75) and (0.75,0.75). Arrangement B touches the boundary and neighboring circles, which the rules allow. These exact-coordinate drawings are teaching illustrations, not measured results from either demonstration or a claim about the best possible four-circle packing.

The score is the sum of radii. Covered area would use π times the sum of squared radii, which is a different objective. We also keep the number of circles fixed when comparing scores. A raw sum for 32 circles cannot establish improvement over a run with 26 circles.

This simple example improves by increasing radii at fixed centers. In a crowded arrangement, further changes can require moving centers: making room for one circle can reduce the room available for others. Finding a good arrangement therefore involves interacting choices. We will use an evolutionary framework to improve the Python programs that search for packings. A program is the method; a packing is the arrangement it produces. We check and score the arrangement to evaluate the method. This strategy can find better constructions without certifying a global optimum.

4. Our strategy: evolve packing programs

How can we improve the method that finds the packings?

Run programs to produce packings. Fitness: the median (middle) score of three complete, valid trials. Keep useful programs as parents.

Luna writes changes to the parent programs. We test each new program before deciding whether to keep it.

We now have a problem and a score. Our proposed strategy improves the programs used to search for packings. Start with a few Python programs. Run them, check that their returned circles obey the rules, and record the sums of radii. The group of programs is the population. Programs chosen for further changes are parents. Luna writes a modified program, called a child. That change is mutation. Running and checking the child tells us whether to keep it, which is selection. Fitness means the measured performance used in that decision; later we define how our three test runs produce it.

Point through the diagram in order. Initialization happens once. Later rounds use selected programs and their results to propose changes. This is the Chapter 10.1 evolutionary loop: the next attempt builds on survivors rather than starting as an unrelated guess. The outside controller stores programs and measurements. Luna’s model weights stay fixed, while the information sent in its next request changes. The checker supplies evidence beyond the model’s explanation of its proposal.

A survivor is a program. Executing it produces a circle arrangement. Keeping a successful arrangement can also provide a numerical starting point for later programs, but that is separate from inheriting program source. Our default demonstration exposes both: program ancestry and a frozen bank of the previous best packings.

6. Classical variation

How can we vary a program without understanding why it works?

Point mutation: change a move scale, for example 0.04→0.020.04\rightarrow0.02. Subtree replacement: replace an acceptance expression. Crossover: inherit code from two parents.

These edits create hypotheses. The evaluator determines whether each resulting program still runs and improves its measured fitness.

Classical variation changes structure; selection supplies direction. Small source edits can have large behavioral effects.

Chapter 10.2.1 introduces point mutation, subtree mutation and crossover using expression trees. Translate that vocabulary to the code students will see. A literal change is a point edit. Replacing an acceptance rule changes a component of the computation. Combining one parent’s constructor with another parent’s search schedule is inheritance from multiple programs. These are conceptual examples, not claims that our controller implements a classical genetic-programming engine.

A move scale controls the distance of a proposed center displacement. Changing it does not by itself say whether a program is better. A smaller scale can help refine a packing but may impede escape from a basin. The complete program must be run and checked under the same trial conditions. This sets up the difference between blind variation and a mutator that reads numerical feedback.

9. Elitism protects measured progress

If a mutation is worse, must the current champion disappear?

Pool parents with the new child. Retain the best complete programs under the declared fitness rule.

For a maximized quality, elitism makes the observed best stay level or improve under comparable evaluation conditions.

A failed mutation need not erase a useful parent. Preserve the best valid packing separately from program fitness.

Chapter 10.3.1 describes carrying elite candidates forward. The lower-is-better course fitness is monotonically non-increasing when the same deterministic measured fitness is used. Equivalently, maximized observed quality is non-decreasing. This is a property of retaining a measured incumbent, not a theorem of global convergence or future quality on new instances.

Our default uses inherited packing banks. At each round, freeze the same incoming packings for the parents and the child, re-evaluate the parents, and select within that bank. An old program median from a different bank is not directly comparable. The cumulative best valid construction is a separate monotone curve because its verified geometry is retained. A valid progress packing can survive in that archive even when a program later times out and receives no eligible fitness.

10. Selection pressure and population collapse

Why can keeping only the highest scores make search stagnate?

Top-kk: rank everyone and retain the best kk. Tournament: sample a group and retain its best; smaller tournaments can preserve more alternatives.

Collapse: several survivors become small rewrites of the same search. Current fitness does not reveal every parent’s future descendants.

Strong selection exploits evidence but can discard useful routes. Our top-three rule does not guarantee diversity.

Chapter 10.3.2 compares top-k and tournament selection; 10.3.3 identifies population collapse. Our implemented rule is deterministic: all three trials must complete and pass geometry checks; then rank by median sum of radii, minimum sum, and stable source identity. A child below the champion may still survive if it belongs among the three best programs. Do not teach elitism as a rule that rejects every nonchampion.

Programs with different IDs may have nearly identical behavior. Normalizing syntax prevents comments alone from creating another genome, but it is not a semantic diversity measure. Several schedules differing only in a constant can still explore the same region. The guide names our three initial mechanisms so students can inspect their differences before deciding whether the population is varied enough. Tournament selection is explained here but is not implemented as a hidden classroom feature.

Packing score: S=∑iriS=\sum_i r_i, after checking the geometry. A scorer that ignores overlap can reward invalid packings.

Chapter 10.4 treats the evaluator as the fitness function and warns that persistent optimization finds weaknesses in it. Here we explicitly compare a flawed scorer with the corrected evaluator, rather than merely presenting an invalid output. The flawed scorer returns the sum of radii and omits pair checks. It ranks two circles of radius 0.30 at centers (0.30, 0.50) and (0.70, 0.50) above two radius-0.25 circles at (0.25, 0.50) and (0.75, 0.50). The claimed gain is 0.10, but the first pair overlaps by 0.20. An optimizer rewarded by that flawed rule has an incentive to enlarge overlapping circles. The correct geometry checker rejects the apparent winner. These are instructor-made, numerically checked toy examples, not Luna outputs. The algorithm guide contains a revealable scorer illustration.

A production witness must contain exactly the required number of finite circle triples. Radii must be nonnegative, circles must fit inside the square, and every pair must avoid overlap. The server independently recomputes both geometry and summed radii; it ignores a program’s claimed score. Numerical tolerance is 1e-9 in unit-square units. A common radius-allocation construction margin of 1e-8 is applied before a final witness is returned and scored. No invalid output is silently repaired during evaluation.

The changing center positions define a nonconvex landscape; the fixed-center radius linear program does not solve that whole problem.

12. Preserve different search behaviors

How can useful alternatives survive beside the current champion?

Islands: evolve separate populations, with occasional migration. MAP-Elites: retain the best program in each behavior bin, such as one-center versus coordinated moves.

Novelty search: favor behaviors unlike those already seen. Different source text alone does not establish different search behavior.

Preserve several ways to search. These are possible extensions; our top-three controller does not implement a diversity archive.

Chapter 10.5.1 motivates preserving several search histories. An island owns a population and mutation history. Occasional migration shares programs; overly frequent migration can make the islands alike, while too little sharing can leave each stalled. Three evaluation seeds are not three islands, and the two circle counts are different problems rather than populations exchanging discoveries.

The Multi-dimensional Archive of Phenotypic Elites (MAP-Elites) organizes candidates by chosen behavior descriptors and keeps a high-quality representative in each bin (Mouret and Clune 2015). For a packing-program archive, illustrative descriptors could measure the typical number of centers moved per proposal and the frequency of restarts. A one-center local search and a coordinated-move search could occupy different bins even if one currently has a lower verified sum. Their quality would still need comparable evaluation conditions. Those descriptors would require instrumentation; the present worker does not record them as a ready-made archive.

Novelty search instead scores behavioral difference from previously observed behaviors (Lehman and Stanley 2011). A possible descriptor distance could use normalized numerical search statistics. It is not a measure of how unusual a program’s variable names sound, and novelty alone does not certify packing quality. These are alternative selection designs whose performance depends on the task and descriptors.

Our controller retains the top three complete programs and rejects exact syntax duplicates. It has no islands, behavioral bins or novelty score. The guide works through the conceptual archive example so students can recognize both its purpose and its absence from the bounded demo.

Chapter 10.5.2 frames the explore–exploit tension. Exploitation refines useful inherited structure; exploration tests a different search mechanism. Internal numerical exploration, such as accepting temporary losses, is different from an outer mutation changing the program. Neither a large source edit nor a fluent hypothesis guarantees an improvement.

The table is invented to explain a decision, not measured Luna performance. Both policies must first be valid and evaluated comparably. B offers 0.01 more quality but takes four more numerical seconds. Neither dominates: A is faster and B has higher quality. A quality–time Pareto view therefore keeps both as options. If we explicitly choose a value of 0.01 quality units per second, maximizing utility U=S−0.01t gives A=2.39 and B=2.36. The price is a teaching assumption, not a measured API tariff or universal preference. A smaller price could reverse the decision.

Chapter 10.8 expresses the corresponding minimization form as cost-adjusted fitness. Cost may mean marginal API dollars or a declared resource measure, with a coefficient that converts units. Generation cost belongs to the path that produced a program; it is not an intrinsic property of source code. Avoid double-counting shared preparation and distinguish per-program evaluation time from all model calls and numerical effort spent finding it. Source length is not automatically a good proxy for either runtime or algorithm quality.

The implemented demo keeps quality primary and reports numerical effort and model usage separately. It does not apply the illustrative price, a complexity penalty or a Pareto archive. Three model calls, 35 seconds per call, eight seconds per trial and a 240-second run deadline bound work. An optional predeclared plateau stopping rule could save further requests; it is not the current automatic policy. The current run can continue its planned rounds after a plateau so students can inspect the mechanism.

No number of calls is universally optimal. Three calls per demonstration are a teaching budget: the first child, a proposal informed by its evaluation, and another chance to inspect adaptation or plateau. This budget is far smaller than the research-scale searches in the AlphaEvolve report. A flat or failed run remains useful evidence. Do not add artificial motion or repeated requests to force a desired trajectory.

Appendix: architecture and API

Optional implementation detail, outside the main presentation schedule.

Appendix A1. One server coordinates the experiment

Who owns the population, execution and measurements?

The controller owns the loop. Only the model worker contacts TAMU; a separate isolated worker executes generated Python.

The same loopback server serves the presentation, demo, algorithm guide, exchange, notes and PDFs. Browser controls create a run, start numerical evaluations and explicitly release each model gate. Server-sent events expose actual progress and support reconnect without repeating work. The model worker alone receives the configured provider credential. The generated program runs inside Bubblewrap with read-only runtime code, no host network and no repository, run-log or private-home mounts. Geometry is checked again in the server outside that code.

Appendix A2. Request, context and source response

What crosses the model API boundary?

Send the task, parent source, current-bank trial results, history and limits. Authorization is a separate HTTPS header.

Return JSON: round_id, parent_ids, hypothesis, source. The source defines solve(initial, seed, steps).

A source string is executable code after admission. The hypothesis is an explanation, never the authoritative score.

The TAMU transport uses protected.gpt-5.6-luna, public streaming and no tools. It sends system instructions plus a JSON response schema and serialized context. The actual body is displayed on the demo page; the key is never part of it. Source identity is normalized syntax plus executor version. An inherited proposal must name actual surviving parent IDs. An independent proposal must use an empty parent list. The controller rejects duplicates and malformed responses without silent retries.

Appendix A3. Execution, checking and feedback

When can a returned program become a survivor?

Validate source → isolated trials → verify every circle and pair → aggregate three complete scores → select within the current packing bank.

Keep exact request/response records, valid witnesses and failures. The next context carries the measured history.

Execution turns a proposal into evidence. Live LLM, numerical-only and recorded replay remain distinct throughout.

Each numerical trial has an eight-second hard wall cap, including its isolated startup. Each model request has a 35-second cap, and the run has a 240-second deadline with bounded owned-process cleanup. Stop and Reset cancel the owned worker tree, not unrelated processes. Missing isolation or dependencies blocks execution instead of falling back to unsafe or fabricated work.

The numerical-only mode evaluates disclosed initial source programs without contacting Luna. Live mode performs real requests only at explicit gates. Replay is registered only from genuine provider records with matching task, source identities, geometry and transcript provenance. It reproduces recorded events, and reveals responses only as its timeline reaches them. Replay is not a new measured result under a changed executor.
